## 1. 产品背景与价值

### 1.1 项目背景

传统天文科普内容常以文字、图表、视频或讲座形式呈现，学习路径较为单向，容易让初学者产生距离感。“假设星星会说话”以星体拟人化为创意入口，让用户以聊天方式主动提问、探索知识，并通过温暖、治愈的表达方式建立情感连接。

本项目计划以 Web 页面形式展示，优先保证低门槛访问、良好的移动端体验和竞赛演示便利性。用户无需下载安装 App，可通过链接直接访问，并在浏览器中完成星体选择、对话互动、科普学习、心愿互动和作品介绍查看。

### 1.2 产品愿景

让天文知识不再只是遥远的名词和公式，而是可以“被听见、被回应、被记住”的星空陪伴体验。

### 1.3 核心目标

1. **科普目标**：以拟人化对话和知识卡片降低天文学习门槛。
2. **互动目标**：让用户主动向星体提问，在互动中获得知识反馈。
3. **情感目标**：营造温暖、治愈、陪伴感强的星空氛围。
4. **竞赛目标**：展示创意性、科普价值、技术实现路径和落地可行性。
5. **展示目标**：以 Web Demo 方式快速演示完整产品闭环。

### 1.4 产品边界

本产品不是专业天文观测工具，也不替代学术级天文数据库。第一阶段以“拟人化科普互动”和“竞赛展示”为主，弱化复杂天体物理计算和专业观测功能。

## 2. 用户分析

### 2.1 核心用户画像

#### 用户 A：青少年学生

* 年龄：8-18 岁
* 特征：对星空、星座、宇宙故事感兴趣，但缺少系统天文知识
* 需求：用简单、有趣、可互动的方式学习天文知识
* 痛点：传统科普文字难理解，专业术语多，缺少陪伴式引导

#### 用户 B：大学生/天文社团成员

* 年龄：18-25 岁
* 特征：有一定天文兴趣，关注作品创意和可实现性
* 需求：体验创新科普表达方式，参与或参考竞赛作品
* 痛点：多数科普产品形式相似，缺少情感化和互动创新

#### 用户 C：竞赛评审/科普教育者

* 特征：关注产品完整度、科普准确性、创新点、传播价值
* 需求：快速理解项目理念、核心功能、技术实现和应用价值
* 痛点：参赛作品常有创意但缺少清晰产品逻辑和落地路径

## 3. 产品定位与差异化

### 3.1 产品定位

“假设星星会说话”是一款以星体拟人化为核心表达方式的天文科普 Web 应用。它通过 LLM 对话、结构化天文知识库和沉浸式星空界面，让用户像和朋友聊天一样学习天文知识。

### 3.2 差异化亮点

1. **拟人化星体人设**：不同星体拥有不同性格、语气和知识表达方式。
2. **对话驱动学习**：用户通过自然语言主动探索，而不是被动阅读。
3. **知识库约束回答**：用结构化科普内容限制模型回答范围，降低错误风险。
4. **情感化科普体验**：加入星空许愿、治愈回应、星体陪伴感。
5. **Web 轻量展示**：适合竞赛路演、移动端扫码访问和线上传播。

## 5. 核心功能需求

## 5.1 首页/星空入口

### 功能说明

首页承担“第一印象”和“竞赛展示入口”作用，需要快速传达产品概念，并引导用户进入核心体验。

### 页面内容

1. 产品标题：“假设星星会说话”
2. 副标题：“和星星聊天，用温柔的方式认识宇宙”
3. 星空背景：深蓝/紫色渐变，星点轻微闪烁
4. 主按钮：“开始和星星对话”
5. 次按钮：“查看作品介绍”
6. 亮点卡片：拟人对话、科普知识、星空许愿、竞赛展示

### 交互要求

* 页面首屏应简洁，不堆叠过多文字。
* 移动端按钮需明显，适合拇指点击。
* 背景动画应轻量，不影响加载速度。

### 验收标准

* 用户进入首页后 3 秒内能理解产品用途。
* 用户能在首屏找到进入对话功能的入口。
* 移动端浏览无横向滚动、无遮挡。

每个星体卡片包含：

* 卡通形象或图标
* 知识标签，如“恒星”“行星”“卫星”“星座文化”

### 交互要求

* 支持按分类筛选：全部、太阳系、恒星、星座。

* 至少支持 8 个可对话星体。
* 每个星体进入对话页后，人设、头像和推荐问题应保持一致。
* 移动端单列或双列卡片布局清晰。

## 5.3 星体拟人对话模块

### 功能说明

用户以文字方式向星体提问，系统返回兼具拟人化表达和天文科普价值的回答。

### 5.3.1 对话输入

#### 功能要求

* 支持用户输入文字问题。
* 支持点击推荐问题快速发起对话。
* P1 阶段支持语音输入。
* 输入框应限制超长文本，建议单次输入不超过 300 字。

#### 示例推荐问题

以“月球”为例：

* “你为什么总是跟着地球？”
* “月亮为什么会有阴晴圆缺？”
* “人类真的去过月球吗？”

以“木星”为例：

* “你为什么有大红斑？”
* “你是怎么保护地球的？”
* “你的卫星有哪些特别的地方？”

### 5.3.2 对话回答

#### 回答结构建议

每次回答建议采用“三段式”：

1. **拟人化开场**：符合星体性格的温暖回应。
2. **科普解释**：用准确、通俗的语言解释知识点。
3. **引导追问**：鼓励用户继续探索。

#### 示例

用户问月球：“你为什么会变圆又变弯？”

月球回答：

> “那是我在阳光下换角度呀。你看到的月相变化，并不是我真的变形，而是太阳照亮我的部分，被地球上的你从不同角度看到了。新月、上弦月、满月、下弦月，都是我绕地球运行时留下的光影日记。你想让我给你画一条月相变化路线吗？”

### 5.3.3 对话安全与边界

系统需限制模型回答范围：

* 允许回答：天文知识、星体故事、星座文化、观星建议、学习引导、星空感悟。
* 谨慎回答：神话传说与科学事实需区分表达。
* 拒绝回答：低俗内容、攻击性内容、无关闲聊、危险建议、伪科学结论。
* 不确定内容：必须提示“我不确定”，并引导用户查看知识卡片或权威来源。

### 5.3.4 知识库增强回答

为降低 LLM 幻觉，建议使用“知识库优先”的回答策略：

1. 根据用户问题识别星体和关键词。
2. 从本地知识库检索相关卡片。
3. 将检索结果和星体人设一起传入模型。
4. 模型基于知识片段生成拟人化回答。
5. 前端展示回答，并可附带“相关知识卡片”。

### 5.3.5 对话历史

MVP 阶段可使用浏览器本地存储保存最近 20 条对话。后续如接入账号系统，可同步到数据库。

### 验收标准

* 用户发送问题后能获得流式或准实时反馈。
* 回答必须同时包含拟人化语气和科普信息。
* 对明显无关问题能进行温和拒答。
* 回答中不能编造关键天文事实。
* 对话页应支持清空当前对话。

## 5.4 科普知识库模块

### 功能说明

科普知识库是产品可信度基础，用于支撑对话回答、卡片展示和小课堂学习。

### 5.4.1 星体科普卡片

每个星体至少包含以下字段：

| 字段   | 示例                 |
| ---- | ------------------ |
| 名称   | 月球                 |
| 类型   | 天然卫星               |
| 所属系统 | 地月系统               |
| 基础参数 | 平均距离、直径、公转周期等      |
| 主要特征 | 月相、潮汐、环形山          |
| 常见误区 | 月亮本身不会发光           |
| 冷知识  | 月球正逐渐远离地球          |
| 文化故事 | 嫦娥奔月、阿尔忒弥斯等        |
| 推荐问题 | 月相为什么变化？           |
| 参考来源 | NASA、ESA、教材、天文馆资料等 |

### 5.4.2 星空小课堂

建议分为 4 个学习单元：

1. **认识太阳系**：太阳、行星、卫星、小行星、彗星。
2. **看懂夜空**：星座、恒星亮度、北极星、银河。
3. **宇宙尺度**：光年、星系、黑洞、宇宙膨胀。
4. **观星入门**：如何选择观星时间、方向、光污染、常见观星工具。

### 5.4.3 知识搜索

支持关键词搜索：

* 星体名称：月球、木星、天狼星
* 概念词：月相、光年、黑洞、流星雨
* 文化词：星座神话、北斗、嫦娥

### 验收标准

* MVP 阶段至少完成 12 个星体卡片。
* 每张卡片至少包含 5 类信息：简介、参数、特征、冷知识、推荐问题。
* 科普内容必须标记来源，内部审核通过后再上线。
* 搜索结果应在 1 秒内返回。

## 5.5 沉浸式星空互动模块

### 功能说明

通过星空视觉、轻量动画和互动反馈，增强产品的情绪价值。

### 功能点

1. 星空背景粒子动画。
2. 当前星体发光动效。
3. 对话时星体头像轻微呼吸动画。
4. 回答生成时显示“星星正在整理光芒……”等文案。
5. 用户获得知识卡片时出现轻提示。

### 视觉原则

* 动效轻量，不喧宾夺主。
* 色彩统一，以深蓝、浅紫、暖白为主。
* 避免复杂 3D 场景影响性能。
* 对低性能设备提供静态背景降级。

### 验收标准

* 首页和对话页具备明显星空氛围。
* 动画不影响文字阅读和输入操作。
* 移动端滚动、输入、点击无明显卡顿。

## 5.6 星空许愿模块

### 功能说明

用户选择一个星体，写下心愿或感悟，系统生成一段符合星体人设的温暖回应。

### 使用流程

1. 用户进入星空许愿页。
2. 选择一个星体或默认随机星体。
3. 输入心愿或感悟。
4. 点击“把心愿交给星星”。
5. 星体返回专属回应。
6. 用户可保存为星愿卡片或分享图片。

### 回应要求

* 语气温暖、积极、治愈。
* 不做现实承诺，如“你一定会成功”。
* 不涉及心理治疗、医疗诊断等高风险内容。
* 可自然融入星体特征。

### 示例

用户写下：“希望考试顺利。”

北极星回应：

> “我不能替你走完那段路，但我可以在夜空里提醒你：方向比慌张更重要。把今天会做的一点点做好，你就已经在靠近自己的星轨了。”

### 验收标准

* 用户能完成一次完整许愿流程。
* 回应符合星体人设，不产生负面或不当引导。
* 可生成适合移动端保存/分享的星愿卡片。

## 5.9 用户中心与本地数据

### 功能说明

MVP 不强制登录，优先使用游客模式。本地保存用户昵称、头像、对话历史、收藏知识点。

### 功能点

* 设置昵称
* 选择默认头像
* 查看最近对话
* 查看收藏知识卡片
* 清除本地数据

### 数据说明

游客模式下，数据优先存储在浏览器 LocalStorage 或 IndexedDB 中。若后续加入账号系统，再同步到云端数据库。

### 验收标准

* 用户无需登录即可体验核心功能。
* 用户可主动清除本地历史数据。
* 不收集无关个人信息。

## 6. 非功能需求

### 6.1 性能要求

| 指标    | 目标                   |
| ----- | -------------------- |
| 首屏加载  | 3 秒内展示主要内容           |
| 对话响应  | 首字响应尽量控制在 3 秒内       |
| 页面切换  | 体感流畅，无明显卡顿           |
| 移动端适配 | 兼容主流 iOS/Android 浏览器 |
| 动效性能  | 低端机可降级为静态背景          |

### 6.2 可用性要求

* 入口清晰，核心路径不超过 3 步：进入首页 → 选择星体 → 开始对话。
* 输入框、按钮、卡片尺寸适合移动端点击。
* 空状态、加载中、失败状态均需有友好提示。
* 对话失败时允许重试，不应让用户卡死。

### 6.3 内容准确性要求

* 结构化知识库内容需先人工审核。
* LLM 回答必须受系统 Prompt 和知识片段约束。
* 对无法确认的问题，不应强行回答。
* 科学事实与神话故事需明确区分。

### 6.4 隐私与安全要求

* 默认不强制登录。
* 不收集真实姓名、手机号、精确位置等敏感信息。
* 若使用模型 API，前端不得暴露 API Key。
* 用户输入需经过基础安全过滤。
* 对话数据如上传服务器，应明确告知用途。

### LLM 推荐策略

MVP 阶段不建议一开始就做复杂 RAG 系统。建议分两阶段：

#### 阶段 1：结构化知识库 + Prompt 约束

* 每个星体有固定知识卡片 JSON。
* 用户提问时，将当前星体资料传给模型。
* 回答必须基于给定资料，不足时提示不确定。

优点：实现快、稳定、适合竞赛 Demo。

#### 阶段 2：向量检索增强

* 将小课堂、科普卡片、参考资料切分为知识片段。
* 存入向量数据库。
* 用户提问时检索相关片段，再生成回答。

优点：知识覆盖更广，适合后续正式版本。

## 16. 最终技术栈结论

### 推荐用于竞赛 Demo 的最终组合

* **框架**：Next.js App Router
* **语言**：TypeScript
* **样式**：Tailwind CSS
* **组件**：shadcn/ui
* **动画**：Framer Motion
* **AI 对话**：Vercel AI SDK + 可替换模型供应商
* **数据**：MVP 使用 JSON；增强版使用 Supabase PostgreSQL
* **存储**：LocalStorage/IndexedDB 保存游客历史
* **部署**：Vercel
* **后续增强**：Supabase Vector 或其他向量数据库做 RAG

### 技术策略

第一版应追求“稳定、好看、可演示”，不要一开始堆过重技术。核心竞争力不是复杂架构，而是：

1. 星体人设是否鲜明；
2. 科普内容是否准确；
3. 对话体验是否自然；
4. 页面展示是否有星空氛围；
5. 竞赛评审是否能快速理解创新点和落地路径。

因此，本项目的开发顺序应为：

> 先完成“Web 可演示闭环”，再增强“真实星图、账号系统、数据看板和向量检索”。
